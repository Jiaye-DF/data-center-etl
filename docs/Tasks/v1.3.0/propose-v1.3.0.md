# Propose v1.3.0

> **草稿**:由 agent 依 user 口述整理,propose 由 user 認可後才生效(`01-propose/01-propose-format.md`);確認 / 修改後即可跑 `/propose-to-tasks`。

## 版本目標

把 v1.2.0 的「整批覆蓋式全量同步」演進為**增量同步**:排程半夜自動偵測來源哪些表有異動,**只同步變動的表**,沒動的整批跳過,大幅降低同步成本與 RDS 寫入量。核心限制:**很多 ERP 表沒有可靠的時間欄、也沒有主鍵**,因此**不採用時間欄 watermark**,改以 **PostgreSQL 內建寫入計數器 `pg_stat_user_tables`(`n_tup_ins` / `n_tup_upd` / `n_tup_del`)** 當變動偵測來源——零掃表、不依賴表結構、不改來源。變動的表沿用 v1.2 的整批覆蓋(TRUNCATE + 重灌,天然涵蓋刪除);同時修正 v1.2 遺留的**排程接線缺口**,讓排程觸發新的鏡像同步而非舊的 config-driven ETL。

## In Scope

- **變動偵測(`pg_stat_user_tables`)**:一句 query 取得來源所有表的累計寫入計數器(`n_tup_ins` / `n_tup_upd` / `n_tup_del`),與自有 DB 記錄的「上次同步時的計數器值」比對:三者皆未增加 → **該表本輪跳過**;任一增加 → 判定為變動、需同步。**零掃表、不需表有時間欄或主鍵**。
- **計數器重置的保守處理**:計數器在來源 DB 重啟 / crash / `pg_stat_reset()` 時會歸零。偵測到計數器**倒退(小於上次記錄值)即視為「有變」**,對該表整批覆蓋一次(寧可多做、不可漏做;半夜跑成本可接受)。
- **增量同步引擎**:`mirror_sync`(v1.2 task-004)加「偵測 → 只灌變動表」路徑;變動表走既有整批覆蓋(TRUNCATE + 分批 INSERT,沿用 v1.2 task-003 `mirror.py`,禁整表物化、禁 DROP)。整批覆蓋天然涵蓋來源刪除。
- **同步狀態存放**:`rds_table_meta` / `sync_states` 加欄位記錄「上次同步時該表的計數器 signature」(`last_stat_ins` / `last_stat_upd` / `last_stat_del` 或等價),供下輪比對;沿用 v1.2 的 `last_synced_at` / `row_count`。
- **排程接線修正(v1.2 遺留缺口)**:`scheduler.py` 目前派工的是舊 `run_etl`(v1.1 逐表 config ETL);本版改為**派工 `mirror_sync`(增量模式)**。排程**預設涵蓋全部表、預設半夜執行**(沿用 v1.2 task-006 友善排程 UI 產生的 cron)。
- **排程管理 UI / model 連動(重要)**:排程現有的「執行範圍 = 指定某張 `etl_table` / 全部啟用表」(`schedules.etl_table_pid`)綁的是 v1.1 config ETL,對 `mirror_sync`(自動偵測全部來源表)**無意義**。本版:
  - 同步排程的執行範圍固定為**「全部來源表(增量)」**,`etl_table_pid` 不適用;排程表單**移除 / 隱藏逐表選擇**,改顯示「增量同步全部表」。
  - 若 v1.1 `run_etl` 需並存 → 排程加 **`job_type`(sync / etl)**,依類型切換表單(sync 無範圍選擇;etl 保留逐表)。若廢除 run_etl 排程 → 直接單一化為同步排程。
  - 排程列表顯示每筆「**做什麼**」(增量同步全部表 / 某張 ETL 表)、下次執行時間、上次執行結果。
  - 沿用 v1.2 task-006 友善 cron picker;**預設時間改半夜**(如 03:00)。
  - **新增 / 編輯排程改用 Dialog(彈窗)**:頁面上**不再直接展開 `ScheduleForm` 內嵌表單**,改為「新增排程」按鈕 → 開 Dialog 填寫(名稱 / 友善 cron / 啟停 / 描述),編輯亦於 Dialog 進行。沿用本版同步確認 Dialog 的彈窗風格(可重用 / 擴充 `ConfirmDialog` 為通用 Modal)。此為**硬需求**:排程管理 UI 一定要調整,不沿用 v1.2 內嵌表單樣式。
- **排程管理頁「依表檢視 + 全表預設納入」**:排程管理**以表為單位**呈現排程涵蓋與執行狀態(不只是列出 cron 條目)。
  - **預設全表納入**:系統保證**每張來源表都被排程涵蓋**——偵測到的表**預設自動納入**夜間增量排程,使用者無需逐張登記(對齊 mirror_sync 全表增量);提供「涵蓋缺口」檢視列出未被涵蓋的表(理論上為 0)。
  - **UI 參照原始資料管理**(schema 分頁籤 + 表清單瀏覽器),但**欄位與查詢聚焦「排程 / 執行狀態」**,與原始資料管理(純看結構)不同:
    - 欄位:資料表(代碼)、業務資料表名稱、**納入排程**(狀態,預設已納入、可排除)、**套用排程**(cron 摘要如「每天 03:00」)、上次同步時間、**上次結果**(成功 / 失敗 / 未跑)、**下次執行**(由 cron 推算)。
    - 資料來源:JOIN `rds_table_meta`(表 + 業務名 + `last_synced_at`)× 排程涵蓋 × 執行紀錄(`etl_runs` / `etl_run_logs` 上次結果)× cron 推算下次執行 —— **非單純讀 metadata 快照**。
    - 篩選:依 schema、依納入狀態、依上次結果、**找未被涵蓋的表**。
  - **排程粒度(決策點)**:預設採**「全表統一夜間排程 + 可逐表排除」**(簡單,mirror_sync 不需依成員過濾);「逐表各綁不同排程」列為選配 / 未來(mirror_sync 需依排程成員決定跑哪些表)。
- **人工全量覆蓋保底**:UI 保留「全量同步」動作 = **強制整批覆蓋全部表(忽略變動偵測)**,供首次灌庫、校正、或懷疑增量漏同步時使用。
- **首次 / 新表基準建立**:自有 DB 無該表計數器基準時(首次上線 / 來源新表),一律**先整批覆蓋一次建立基準**,之後才進入增量比對。

## Out of Scope

- **CDC / 邏輯複製(WAL / Debezium / logical replication slot)**:逐筆增量、低延遲、精準攔截刪除的「真‧增量」——**本版不做**,列為未來版本;需開 RDS `rds.logical_replication`、常駐 consumer、管 replication slot,屬較重投資。
- **逐筆 row-level upsert(`INSERT … ON CONFLICT`)**:本版變動表一律**整批覆蓋**,不做逐筆增量(多數表無可靠主鍵 / 時間欄,逐筆判斷不可行)。
- **改動來源**:一律**不改來源**(不加 trigger、不改 schema、不改識別字);沿用 v1.2 唯讀來源原則。
- **時間欄 watermark**:因多數 ERP 表無可靠時間欄,**明確不採用**日期欄增量。
- **通知 / 告警、水平擴充**:沿用既有 Out of Scope。
- **Coolify 正式部署 / 上雲**:本版仍以 localhost `docker compose` 可跑為準。

## 對外承諾

- 排程到點(半夜)自動觸發**增量同步**:先讀 `pg_stat_user_tables` 判斷哪些表有異動,**只對變動表整批覆蓋**,未變動表跳過;執行紀錄(etl_runs / etl_run_logs)可查得本輪跳過 / 同步的表數。
- 連續兩次排程之間某表在來源沒有任何增 / 改 / 刪 → 第二次同步**不會重灌該表**(log 顯示 skip)。
- 某表在來源有異動(含刪除)→ 下次同步該表被判定變動並整批覆蓋,hub 反映最新內容。
- 「全量同步」人工動作仍可**強制覆蓋全部表**,不受變動偵測影響。
- 排程 UI(v1.2 已有)建立的排程,現在**真的會觸發鏡像同步**(而非舊 config ETL)。
- 排程管理頁**新增 / 編輯排程改用 Dialog 彈窗**(不再頁面內嵌表單);建立同步排程時不需選「哪張表」,直接是「全部表(增量)、半夜」;排程列表看得出每筆**做什麼**與**上次執行結果**。
- 排程管理頁**以表為單位**呈現:每張來源表**預設已納入**夜間排程,看得出套用排程、上次同步結果、下次執行;可一眼確認「全部表都被涵蓋」,並找出未涵蓋的表。

## 風險與相依

- **`pg_stat_user_tables` 特性**:計數器為**累計、近似值**,需 `track_counts`(RDS 預設開);DB 重啟 / crash / 手動重置會歸零。對策已納入 In Scope(倒退即整灌)。極端情況:計數器歸零後又剛好累加回接近原值,理論上可能漏判——半夜低頻 + 週期性強制全量覆蓋(可選)可校正。
- **無法偵測「同筆先刪再增回」等淨零變動**:若某表增刪相抵使某計數器看似未動——實際上 `n_tup_ins` 與 `n_tup_del` 是**各自累加不相抵**,故一般變動都會被抓到;風險低。
- **排程語意變更**:排程改派 `mirror_sync` 會**改變既有 `run_etl` 排程行為**。需決策:v1.1 config-driven ETL(`run_etl`)是**保留並存**(排程可選類型)還是**廢除**。預設建議:本版排程一律走 `mirror_sync`,`run_etl` 手動保留、不再由排程觸發(待 user 確認)。
- **`schedules.etl_table_pid` 失去意義**:sync 排程對「哪張表」無概念(mirror_sync 全表增量)。並存則加 `job_type` 區分;廢除則欄位**保留 NULL / 標記 deprecated**(**禁 DROP COLUMN**,依既有毀滅性操作禁止)。前端表單移除逐表選擇需同步處理既有排程資料相容。
- **首次上線大量整灌**:所有表無基準 → 首輪等同一次全量同步(大規模 RDS 寫入);建議首輪由 user 手動確認後於半夜執行。
- **RDS 寫入仍不可逆**:變動表整批覆蓋 = TRUNCATE + 重灌(禁 DROP);沿用 v1.2 分批串流。
- **前置相依**:v1.2.0 需已落地(`mirror_sync` / `rds_table_meta` / 排程友善 UI);來源 `erp_migration_test` 可讀、目標 `erp_etl_hub_test` 可寫;RDS 連線走 `.env` `AWS_RDS_*`。

## 驗收標準

- 連續兩次同步之間某表**未異動** → 第二次同步該表被 **skip**(未寫 hub;log / run_logs 可證,hub 該表 `last_synced_at` 不更新)。
- 某表在來源**新增 / 更新 / 刪除**若干筆 → 下次同步該表被判定變動、整批覆蓋,hub 內容 = 來源最新(含刪除已反映)。
- 模擬計數器重置(`pg_stat_reset()` 或值倒退)→ 相關表被判定變動並整灌,**不漏同步**。
- **排程到點**(以測試用近期 cron 驗)自動觸發 `mirror_sync` 增量模式;執行紀錄出現對應 run。
- 人工「全量同步」→ **忽略偵測、強制覆蓋全部表**。
- 首次(無基準)→ 全表整灌建立計數器基準;第二次(無異動)→ 全表 skip。
- **排程管理 UI**:「新增排程」按鈕開 **Dialog** 填寫(非頁面內嵌表單);同步排程無逐表選擇、預設半夜全部表;排程列表顯示每筆行為與上次執行結果;編輯既有排程亦於 Dialog 進行。
- **排程管理依表檢視**:排程管理頁以 schema 分頁 + 表清單呈現;每張表預設「已納入」夜間排程,欄位含套用排程 / 上次結果 / 下次執行;可篩出「未被涵蓋的表」(應為 0);新偵測到的表自動納入,無需逐張登記。
- localhost `docker compose up` 全流程可跑;瀏覽頁不受半夜同步影響(讀快照 / cache)。

## 背景參考(非 scope,供拆 task 對照)

- **v1.2.0 已落地**:`mirror_sync` worker task(task-004)、`mirror.py` 整批覆蓋引擎(task-003,TRUNCATE + 重灌 + DS 字典 COMMENT)、`rds_table_meta` 快照(task-001)、快照服務 + Redis(task-002)、排程友善 UI(task-006)。本版於其上加變動偵測 + 修排程接線。
- **排程接線現況**:`app/worker/scheduler.py` 的 `RUN_ETL_TASK_NAME = "run_etl"`,`build_scheduled_tasks` 派工舊 `run_etl`(逐表 config ETL);本版改派 `mirror_sync`。
- **變動偵測查詢**:`SELECT relname, n_tup_ins, n_tup_upd, n_tup_del FROM pg_stat_user_tables`(對 source RDS,一次取全表計數器,零掃表)。
- **概念釐清(避免誤解)**:Redis cache 只存瀏覽頁的「表清單 / schema 清單」(短 TTL),**不存資料列**;真實資料列在 hub RDS(`erp_etl_hub_test`);快照 metadata 在自有 DB。Cache 保護的是瀏覽體驗,不是資料正確性——同步正確性仍需由 hub 資料保證。
- **未來版本候選**:CDC(PostgreSQL 邏輯複製 / Debezium)做逐筆、即時、精準抓刪除的真增量,適合要低延遲或精準刪除偵測時再上。
