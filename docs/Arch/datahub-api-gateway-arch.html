DataHub API Gateway 細節架構

對應〈地端 → AWS 資料中樞架構〉第六層「DataHub API Gateway」的模組內部展開；各模組可點開「詳細設計」查看流程圖與資料模型。

  • 串接方：外部應用系統（API Client · 機器對機器）
  • 驗證：Client Credentials 換發 15 分鐘短效 JWT（後台管理介面才走 DF-SSO）
  • 權限階層：系統別 → 作業 → 角色權限設定檔 → Role；設定檔授權細到 Profile → Operation → Table → Column → Read / Edit
  • 綁定：API Client 只綁 1 個 Role（0..1）＋ 特例權限 0..N（臨時分派、可設效期）
  • 最終欄位 = 設定檔在該作業下勾選的欄位與動作（∩ 作業範圍）；沒給 = 不回傳；Edit = 新增 / 更新 / 刪除（刪除一律軟刪除）
  • 每筆請求先完成權限判斷，才以統一封套回傳只含授權欄位的語意 JSON

模組①

API Client 連接層（JWT 驗證）

Phase 3A 進行中

Client Credentials 取得 token · 短效 JWT 本地驗簽 · 流量控管

  • 所有外部請求的唯一入口
  • 取得 token：client_id + client secret 打 /token（首次）或 /refresh_token（過期換新）→ 15 分鐘短效 JWT
  • 資料 API：Bearer JWT 本機驗簽 — 不回源、不查資料庫；驗不過直接 401，不進入後續模組
  • 通過後組請求上下文（哪個 Client · 哪個作業 · 哪些欄位）交給權限引擎
Client Credentials OAuth2 M2M 短效 JWT 15 分鐘 本地驗簽 不回源 · 不查 DB Rate Limit per Client 對外路由 /api/client/v1.0/*
📋 詳細設計 — 路由總表 · token 取得 / 驗簽流程 · 錯誤碼 · 抗壓設計

路由命名空間：對外 /api/client/{version}/{service} · 後台 /api/v1

  • 對外串接一律 /api/client/{version}/{service}/...；{service} = 系統別（erp / crm / hrm / bpm / zpos…），作業歸屬系統別底下，路由 / 授權 / 稽核都好維護
  • token 端點不分 service：一個 Client 一份身分，通用全部 service
  • 後台管理（模組②，管理員經 DF-SSO）沿用既有 /api/v1/... 不動；兩個命名空間分開，middleware / 限流 / 稽核策略各自掛

對外路由總表（/api/client/v1.0）

路由驗證方式用途
POST /api/client/v1.0/tokenclient_id + client_secret（比對雜湊）首次取得 access token（短效 JWT）；secret 放 body 不放 query
POST /api/client/v1.0/refresh_token過期 access token + client_id + client_secret換新 token（語意刷新，不發 refresh token）；額外驗舊 token 簽章有效（忽略 exp）且 sub = client_id，防交叉取得 token
GET /api/client/v1.0/{service}/operations（選用）Bearer JWT（本地驗簽）列出該 Client 在此 service 已授權的作業；未授權的作業連名字都不出現
GET /api/client/v1.0/{service}/operations/{operation}Bearer JWT（本地驗簽）執行作業查詢（需 read）：展開作業的表 × 欄位範圍 ∩ 表欄位授權，data 依表分組回傳；fields / 分頁 / 篩選參數
POST / PATCH / DELETE /api/client/v1.0/{service}/operations/{operation}（規劃）Bearer JWT（本地驗簽）作業寫入：需該表欄位 edit 權限；DELETE 一律軟刪除（is_deleted），禁物理刪除
💡 /refresh_token 的定位它同樣要帶 secret，安全上與 /token 等價 — 價值在語意與稽核：驗舊 token 簽章（擋垃圾字串）、驗 sub 一致（拿 A 系統過期 token + B 系統 secret 不給換），稽核可追蹤 token 世代鏈。

版本策略與資料夾結構（/api/client 專用）

  • 不把所有 router 塞進單一 v1/ 資料夾
  • 共用邏輯與 service 模組「版本無關」，版本層只是薄薄的掛載設定
  • 新版本只宣告與前版的差異（override），沒改的端點自動沿用 — 避免每出一版就整包複製

錯誤碼約定

情境回應說明
secret 錯誤 / Client 已停用（/token · /refresh_token）401 invalid_client不區分「Client 不存在」與「secret 錯誤」，防列舉
舊 token 簽章無效 / sub ≠ client_id（/refresh_token）401 invalid_client與 secret 錯誤同一種回應，不透露是哪一項不過
JWT 缺失 / 過期 / 簽章無效（資料 API）401 Unauthorized串接方收到即打 /refresh_token 換新 token 再重試
token 端點爆破 / 連續失敗429 + 暫時鎖定以 client_id + 來源 IP 計，低頻上限
資料 API 流量超限429 Too Many Requestsper Client 額度，附 Retry-After

  • detail 僅基本錯誤資訊，不洩漏內部設計

抗壓設計（防打崩）

防線做法擋什麼
JWT 本地驗簽資料請求的驗證零外部回源、零 DB 查詢高頻請求打爆驗證依賴（測試站曾因每請求回源 SSO 驗證 429 → 502）
/token · /refresh_token 嚴格限流token 取得天生低頻（約 15 分鐘一次），設低額度 + 連續失敗鎖定（失敗計數與鎖定旗標同樣放 Redis，帶 TTL 自動解鎖）secret 爆破、token 請求風暴
per-Client Rate Limit各系統獨立額度 + 全域總上限；計數器放 Redis（INCR + TTL，跨 worker / 實例共用，key 格式 rate_limit:client:<client_id>）；參數存 DB（預設 30/分、200/10 分），後台可逐 Client 調整單一串接方失控（迴圈狂打）拖垮全體；in-process 計數在多 worker 下額度會 × worker 數失效
Redis 故障策略限流 / 鎖定 fail-open（Redis 不通 → 放行 + 大聲告警）避免 Redis 變成資料供應的單點故障；內網場景限流是防失控、不是防攻擊
分頁強制上限limit 封頂（如 ≤ 1000）+ 查詢逾時一條大查詢拖垮 ETL-Hub
網路層SG 只放內網 / VPN CIDR，不開公網直接砍掉外部攻擊面
✅ 與 DF-SSO 的分工資料 API 完全不經 DF-SSO — JWT 由 Gateway 自簽自驗，token 有效期內對外零依賴；DF-SSO 僅用於後台管理介面的管理員（人）登入。
模組②

DataHub 後台 · 組織權限管理

Phase 3A 設計焦點 規劃中

權限階層：系統別 → 作業 → 角色權限設定檔 → Role · 特例權限直綁 User · 管理員經 DF-SSO 登入

  • 權限的維護面：管理介面是人用的，管理員以 DF-SSO 登入
  • 階層由下而上：
    • 系統別（Service）：erp / crm / hrm / bpm / zpos… — 作業的分類容器
    • 作業（Operation）：歸屬一個系統別，定義此業務動作需要的表 × 欄位範圍
    • 角色權限設定檔（Profile）：授權階層 Profile → Operation → Table → Column → Read / Edit — 欄位與動作授權的主要來源
    • Role：綁定 1 個設定檔（必綁、禁空）
  • API Client（User）只綁 1 個 Role（0..1）；臨時需求走特例權限（結構同設定檔，直綁 User、可設效期）
  • 最終權限 = Role 設定檔 ∪ 特例權限；最終欄位 = 設定檔在該作業下勾選的欄位與動作（∩ 作業範圍），沒給 = 不回傳
  • Edit = 新增 / 更新 / 刪除（刪除一律軟刪除，禁物理刪除）
  • Salesforce 式加法模型：只授予、無 deny；並管理 client secret 的發放 / 輪替 / 停用

🗂 系統別（Service）

erp / crm / hrm / bpm / zpos… 作業的分類容器，對應路由 {service} 分段。

📦 作業（Operation）

歸屬一個系統別。定義此動作需要的表 × 欄位範圍（例：O1 → T1 · T2 · T3 的指定欄位）。查詢入口與範圍上限，不決定最終回傳欄位。

📋 角色權限設定檔（Profile）

授權階層：Profile → Operation → Table → Column → Read / Edit（* = 全欄位）。綁作業後，在每個作業底下逐表逐欄設動作 — 欄位與動作授權的主要來源。被 Role 綁定。

🎭 Role 區塊

綁定 1 個角色權限設定檔（必綁、禁空角色）。User 的唯一基準權限包，純為方便管理。

🧩 特例權限

臨時分派用：把某作業 / 某些表欄位直接給某個 User，可設效期；不污染 Role 與設定檔。

🔑 API Client 區塊

一個外部應用系統一個 Client（= User）。只綁 1 個 Role（0..1）＋ 特例權限 0..N，管理 secret 發放 / 輪替 / 停用，可預覽最終可見欄位。

加法模型 只授予、無 deny 聯集 Role 設定檔 ∪ 特例權限 系統別 erp · crm · hrm · bpm · zpos… 作業 授權入口 · 表 × 欄位範圍 粒度 資料表 × 欄位（跟表走） secret 只存雜湊 · 雙鑰輪替 對照 Salesforce Profile / Permission Set

權限引擎（AuthZ Engine）

Phase 3A 規劃中

聯集展開 · 作業 → 表 → 欄位三段式判斷 · 權限快取

  • 權限的判斷面：每筆請求執行三段式判斷
  • 聯集展開：Role 設定檔 + 特例權限（過濾已過期）→ {作業: {表: {欄位: read/edit}}}；TTL 快取、後台異動即失效

  • 逐表交集：展開作業的表 × 欄位範圍，取設定檔在該作業下的欄位與動作（查詢需 read、寫入需 edit）
  • 沒給表欄位授權 → 交集為空 → 回傳空資料（作業只給入口與範圍）
  • 結果交給資料供應模組逐表組 SQL

權限模型

名詞對照 / 類型說明
Role（角色）名字與指派的載體綁定 1 個角色權限設定檔（1:1、必綁、禁空）；Client 只綁 0..1 個，純為方便管理。
角色權限設定檔（Profile）常規授權內容授權階層 Profile → Operation → Table → Column → Read / Edit — 欄位與動作授權的主要來源；沒給 = 不回傳任何欄位。
特例權限臨時分派結構同設定檔（作業 + 表欄位授權），直接綁 User、可設效期（expires_at）；到期自動失效，不污染 Role 與設定檔。
作業（Operation）業務動作單位定義此動作需要的表 × 欄位範圍（operation_items）；查詢入口與範圍上限，方便管理 — 不決定最終回傳欄位。歸屬一個系統別。
系統別（Service）分類容器 / 路由分段erp / crm / hrm / bpm / zpos…（services 表）；作業歸屬系統別，路由為 /api/client/{version}/{service}/...；token 端點不分 service。
權限項profile_items / exception_items一筆 = 某作業下某表的某欄位 + 動作（read / edit；'*' 為全欄位）；edit 含新增 / 更新 / 刪除，刪除一律軟刪除。
聯集 / 加法模型Additive（無 deny）最終權限 = Role 設定檔 ∪ 特例權限；只授予不拒絕，收權靠改設定檔 / 解除綁定 / 特例到期。
effective 權限{作業集合} + {表: 欄位}Role 設定檔 + 特例權限聯集展開後供判斷的記憶體結構；TTL 快取、後台異動即失效。
作業級 / 表級 / 欄位級三段式判斷先看作業授權（無 → 403），展開作業的表 × 欄位範圍，逐表取「範圍 ∩ 表欄位授權」；沒給 → 回傳空。

名詞全稱 / 類型說明
