◆ Phase 3A · 架構設計

Data Hub API Gateway — 統一資料出入口設計

把 ETL-Hub／語意層的高品質資料，以單一出入口對外供應：權限管理落 RDS、 讀寫拆成兩個獨立應用、由 Coolify 部署於 2 台 EC2 —— 一邊故障不影響另一邊。

業務系統 / Agent→ DF-SSO / API Key 驗證→ API Gateway（讀 / 寫分離）→ 權限檢核（RDS）→ ETL-Hub / 語意層
定位　治理架構第四層 Data Hub 中央平台的對外供應層 現況　讀取側已在 data-center-etl；寫入側為本設計新建
1

設計目標 — 為什麼需要 API Gateway

應用系統目前若要用資料，只能直連資料庫 —— 權限難控管、行為無法稽核、任何一個應用都可能拖垮共用資源。Gateway 要一次解決這四件事。

🚪統一出入口

應用系統與 Agent 一律經 API 取用、不直連資料庫。新應用接入只需申請權限，不需重新接資料來源。

🔐權限收斂

誰能讀哪些資料集、誰能寫哪些表，授權定義集中存 RDS，一處管理、兩個應用共用同一套授權事實。

🧱故障隔離

讀取與寫入拆成兩個獨立應用、兩台 EC2：寫入服務故障或被打掛，查詢供應完全不受影響（反之亦然）。

🧾行為可稽核

誰、何時、取／寫了什麼，全數留痕；搭配 Rate Limit 防止單一消費端耗盡資源。

設計原則（延續整體架構）Private First · 最小權限（DB 帳號也分讀寫）· 沿用既有元件（DF-SSO、Redis／Taskiq、Coolify）不重造輪子。

3

權限管理 — 授權資料落 RDS，一套模型兩應用共用

人用 DF-SSO 登入管理介面維護授權；系統對系統（業務系統呼叫 API）用 API Key + scope。授權定義全部存 RDS，讀寫應用各自檢核、不互相依賴。

🗄️授權資料模型（RDS）

  • api_clients — 消費端註冊：名稱、API Key（hash 存放）、狀態、負責單位
  • api_scopes — 能力範圍：read:dataset / write:table
  • api_grants — client ↔ 資料集（schema / table 粒度）的授權對應，含到期日與軟刪除
  • api_access_logs — 每次呼叫留痕：client、動作、資料集、筆數、結果
⚠ 底線API Key 只存 hash、不落明碼；授權異動本身也要寫稽核（誰授的權）。

4

讀取應用 — 落在現有 data-center-etl 已有基礎

資料集瀏覽、查詢、語意層 JSON 轉換與 SSO 整合都已存在 —— 缺的是把「對外供應」的權限中介層與稽核掛上去。

元件現況本設計要補的
資料集瀏覽 / 查詢 API已建置（管理平台內部用）對外版 endpoint：介面版本化（/api/v1/datasets）、分頁與筆數上限
語意層已建置（英文 key JSON / _view）對外回傳一律走語意層，不暴露原始代號欄位
身分驗證已建置（DF-SSO，人員登入）加上 api_clients API Key 驗證（系統對系統）
權限範圍 / 稽核缺口掛上六道檢核鏈（授權表 + access_logs）
Rate Limit / 安全 Headers缺口（scan 遺留 High）部署前必補：依 client 配額限流
DB 帳號單一帳號Read API 改用唯讀 DB 帳號（最小權限）
為什麼讀取放這裡資料、語意層、SSO 都在這個專案，重用成本最低；且讀取是「供應」的主力流量，與既有管理平台同一個故障域可接受 —— 真正要隔離的是寫入。
5

寫入應用 — 獨立新專案 + 第二台 EC2 目前缺口

寫入路徑風險本質上高於讀取（改資料、鎖表、量突發），所以獨立成專案、獨立部署。寫入不直接落庫 —— 走佇列非同步，天生具備削峰與重試。

寫入路徑 — 收單即回 202，佇列非同步落庫；冪等鍵防重送、白名單限定可寫 schema

🧬與 ETL 的邊界

寫入目標是獨立的應用資料 schema（如 app_ingest），不寫 Raw、不寫 ETL-Hub 同步表 —— 不與 DMS / mirror_sync 打架。

♻️沿用既有技術

Redis 佇列、Taskiq Worker、Docker Compose、Coolify 部署 —— 與 ETL 同一套技術棧，維運心智成本最低。

🔑專用 DB 帳號

寫入帳號只授權指定 schema 的 INSERT / UPDATE；無 DDL、無跨 schema，錯誤半徑鎖死。

6

故障隔離 — 拆兩台的理由：故障域分析

「一個壞了不影響另一個」不是口號 —— 逐一檢視故障情境，確認隔離邊界真的成立。

故障情境影響範圍另一側恢復手段
寫入應用 crash / OOMEC2-B 的 Write API讀取照常 ✓Coolify 自動重啟；佇列訊息不遺失、重啟續跑
讀取應用被查詢打滿EC2-A 的 Read API 變慢寫入照常 ✓Rate Limit 降載；查詢筆數上限擋大查詢
EC2 整台故障該台上的單一應用另一台不受影響 ✓Coolify 重新部署到替補機
部署出錯（壞版本上線）單一應用另一應用不同專案、不同 pipeline ✓Coolify 一鍵回滾
Redis 故障寫入暫停收單（回 503）讀取不依賴 Redis ✓Redis 重啟後續跑；client 依 202/503 重試
RDS 故障讀寫皆停 ✗（唯一共用點）—RDS 是既有共同依賴：Multi-AZ（正式環境）+ 備份還原
⚠ 誠實面對唯一單點RDS 是兩側唯一共用資源 —— 這是刻意的取捨（資料只有一份事實）。緩解靠 RDS 本身的可用性手段（Multi-AZ / 快照），而不是在應用層做花活。

方案比較（討論）— 為什麼選讀寫分離雙機

把「省成本」與「隔離強度」攤開比較 —— 結論是採方案 A，但列出 B 作為預算受限時的退路。

面向A · 雙 EC2 讀寫分離
（本設計）		B · 單 EC2 雙容器C · 單一應用含讀寫
故障隔離✓ 主機級隔離，最強△ 容器級：應用互不影響，但主機掛全掛✗ 同進程，一個 bug 全倒
部署風險✓ 兩條 pipeline，互不牽連✓ 可分開部署✗ 改寫入也要重佈讀取
資源競爭✓ 完全獨立△ 需設容器資源上限✗ 大查詢與大寫入互搶
成本△ 多一台 EC2✓ 單台✓ 單台
維運複雜度△ 兩專案兩機（Coolify 統一管理可控）△ 兩專案一機✓ 最簡單
擴展路徑✓ 讀寫各自水平擴展、可各自加機△ 擴展時終究要拆機✗ 只能整包放大
✅ 結論採 方案 A：寫入路徑風險高、且讀取是對外供應的生命線，主機級隔離值回一台 EC2 的成本。若初期預算受限，方案 B 為可接受的過渡（同機雙容器 + 資源上限），日後把寫入容器搬到第二台即可、應用程式碼零改動。
8

建議增強（討論）— 在原設計上追加五項

方向不變（雙機讀寫分離 + 權限落 RDS），以下是讓它更穩、更好維運的增強項，供討論取捨。

🌐① 統一入口網域

用 Coolify 內建反向代理給兩個應用同一個網域、不同路徑（api.example.com/read/*、/write/*）或子網域。消費端只記一個入口，底層搬機、擴機不影響對接。

🔑② DB 帳號讀寫分離

Read API 用唯讀帳號、Write Worker 用限定 schema 的寫入帳號 —— 就算應用被打穿，資料庫層還有一道最小權限防線。

📥③ 寫入一律走佇列

收單即回 202 + 追蹤 id，落庫交給 Worker：天生削峰、可重試、可冪等；寫入量暴增時排隊而不是壓垮 RDS。

🧾④ 檢核鏈做成共用套件

六道檢核鏈以共用套件形式讓兩個專案引用（同一套邏輯、各自部署），避免規則兩邊漂移；限流計數放 Redis（讀取側可用獨立 Redis db 或記憶體限流，維持不依賴）。

📈⑤ 預留讀取擴展位：RDS Read Replica

讀取量若成長，優先開 RDS 讀取複本讓 Read API 指向 replica —— 讀寫在資料庫層也分流，寫入鎖表不影響查詢。這一步現在不做，但連線設定先以環境變數區分 reader / writer endpoint，日後零改碼切換。

9

落地步驟 — 從現況到上線：六步走

先把授權模型立起來（兩側共用），再讓讀取先上線供應、寫入隨後 —— 每一步都可獨立驗收。

#步驟範圍驗收
1授權表 schema 落 RDSapi_clients / scopes / grants / access_logs + Alembic migration管理介面可建 client、發 Key（hash 存放）
2Read API 掛檢核鏈現有 data-center-etl：對外 endpoint 版本化 + 六道檢核 + 唯讀 DB 帳號未授權 401/403、授權 client 可查、access_logs 有痕
3Rate Limit + 安全 Headers讀取側（scan 遺留 High，部署前必補）超額回 429；安全掃描過
4Write 專案 scaffold新 repo：FastAPI + Taskiq Worker + 檢核共用套件 + app_ingest schema本地 Docker Compose 全流程通（202 → 落庫 → 稽核）
5第二台 EC2 + Coolify 接入寫入應用獨立部署、專用寫入 DB 帳號雙機各自部署 / 回滾互不影響
6上線驗證故障演練：關掉寫入側驗證讀取不受影響（反之亦然）故障域表逐項打勾
待決事項（需要拍板） ① 第二台 EC2 規格與成本上限（或先走方案 B 過渡）； ② 允許寫入的資料範圍（app_ingest 收哪些業務資料）； ③ 與 ERP 回寫議題的關係 —— 本設計只寫自有 RDS，不回寫 ERP（回寫另案評估）； ④ Rate Limit 配額標準（依 client 或依部門）。
